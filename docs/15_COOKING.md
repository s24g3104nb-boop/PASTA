# 完成料理：手動選択と材料ベースの栄養計算

同じ履歴IDの二重使用は拒否するが、同じ物理的な乾麺を異なる履歴IDで重複計測した場合は自動判定できない。保存済み料理の計算条件は固定し、料理履歴の編集画面はまだ実装していない。

## 現在使える範囲

Streamlitの「完成料理」タブで、乾麺の計測履歴を明示的に選び、同じ調理バッチに
使ったことを確認します。料理名は手動選択です。分類器は未学習で、写真を見て
料理名・材料量・重量・総カロリーを判別したと表示する機能はありません。
`dish_classifier.py` の `UntrainedDishClassifier.predict` は常に `untrained` を返し、
ラベルとスコアは `None` です。学習済み分類器を接続するための境界だけを設けています。
分類学習・データ収集は今後の段階です。

材料名、使用量(g)、100gあたりkcal/P/F/Cを入力します。卵1個なども食べる部分の
gへ換算し、製品表示や確認した食品成分値を使用してください。材料候補は確認用の
名前だけで、量や栄養の標準値は入りません。利用者が登録したレシピは後述の手順で
参考にできます。未入力・NaN・無限大・負数は拒否します。
本当に0と分かる場合だけ0を入力してください。使わなかった材料は追加しません。
材料をすべて入力した旨の確認なしに計算を確定できません。

乾麺分 + 各追加材料の `使用g × 100g栄養値 / 100` を合計し、等分人数または
食べる割合で按分します。計算途中は丸めず、表示で小数1桁にします。
この結果は入力した前提に基づく計算値であり、写真からの栄養実測ではありません。

## 利用者登録レシピを再利用する

今回の材料入力をテンプレートとして登録できます。名前、料理名、基準乾麺g、基準人数、
各材料のg・100g栄養値、出典と分量の前提が必要です。アプリが架空の数値を補うことは
ありません。料理名に合う登録テンプレートを選ぶと、材料gを
`今回の乾麺g / テンプレートの基準乾麺g` 倍して仮入力します。基準人数も表示・仮入力
されるため、今回の取り分け人数を確認・変更してください。材料量は自由に編集できます。

テンプレートを使う場合は、仮分量を確認・修正した旨の明示的な確認が必要です。
計算結果は `nutrition_basis=template_estimate` として保存し、「利用者登録レシピに
基づく概算」と常に表示します。テンプレート名、出典、基準分量、当時の内容も固定保存する
ため、元テンプレートを削除しても過去の計算根拠は残ります。直接入力した場合は
`confirmed_amounts` として区別します。乾麺gの実測／推定の区別は、どちらでも別途表示します。

テンプレート一覧・削除も料理タブで行えます。削除はレシピだけに作用し、料理履歴は
削除しません。編集した内容を保存する場合は別の名前で新規登録してください。

Python APIは `save_recipe_template`、`list_recipe_templates`、
`delete_recipe_template`（`cooking_storage.py`）、乾麺g比での展開は
`template_ingredients`（`cooking.py`）です。

## 既存履歴との互換性

既存の `products` と `measurements` は変更・削除しません。
`cooking_storage.init_cooking_db` は `cooking_sessions`、`cooking_ingredients`、`recipe_templates`
を追加し、何度実行しても既存の料理記録は残ります。料理記録は計測履歴IDを外部キーで
参照し、選んだ乾麺のスナップショット、全材料の値、按分条件、計算結果を固定保存します。
後で製品情報や計測行を編集しても、過去の料理計算結果は変わりません。

乾麺の重量は `actual_g` があれば実測、それ以外は `estimated_g` を使います。
計測時の製品100g栄養値が保存されている履歴では、その値から再計算します。
旧履歴に製品スナップショットがない場合、保存済み栄養値を
`使用重量 / 当時の推定重量` で補正します。この方法には当時の丸め誤差があります。
0gの推定履歴からは100g栄養値を復元できないため拒否します。
CG/デモ製品ではデモである旨、来歴不明の旧履歴では確認が必要な旨を表示します。

同じ乾麺履歴IDから新しい料理を2回保存することはできません。
`BEGIN IMMEDIATE` のトランザクション内で使用済みか確認してから登録するため、
同時送信でも二重登録を防ぎます。複数人分を作った場合は1つの料理記録の人数・割合で
按分してください。過去に重複登録された料理は消さず、履歴で重複件数の警告を表示します。
料理履歴の更新・取消機能は未実装です。新規の乾麺測定を作って同じ食事を複製すると
二重計上までは検出できないため、同じ調理バッチであるかの利用者確認も維持しています。

初回使用前には既存SQLiteとphotosを通常のバックアップ手順で保管してください。
アプリ停止中のコピー、またはSQLite Backup APIを使用します。移行は追加のみですが、
古いアプリで料理履歴を表示する機能はありません。

## テスト

リポジトリ直下から実行します。

```sh
python -m pytest -q pasta_weight_app_v2/tests/test_cooking.py pasta_weight_app_v2/tests/test_cooking_ui.py
```

350kcalの乾麺と追加250kcalの合計600kcal、2等分300kcal、量変更、未入力拒否、
未学習分類器、同一バッチ確認、存在しない計測ID、旧履歴の保持を検証します。
テンプレートの登録・比率展開・削除後の計算根拠保持、未確認時の拒否、概算表示、
同時保存の二重計上防止、旧重複データ保持も確認します。
試験の食材栄養値は架空の計算確認値です。

## 次の段階

許諾・出典・撮影グループ・料理クラスを管理した分類用データセットを別途準備します。
カルボナーラ・ボロネーゼ・ミートソース等のクラス定義を決め、独立した実写で評価し、
低信頼・未知料理を不明として返すモデルを接続します。材料量と栄養値の入力経路は
料理分類とは独立して維持します。外部公開の認証とユーザー別データ分離、実機検証は未対応です。
